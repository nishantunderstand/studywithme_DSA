This is roughly how the hour goes when I take interviews:  
  
• 5 min: introductions  
• 2–3 min: rules and setup  
• 5 min: clarifying the problem  
• 10 min: discussing the approach  
• 20 min: coding  
• 10 min: dry run and follow-ups  
• 5 min: your questions for me  
  
So only about a third of the hour is actual coding. The rest is understanding the problem, explaining your thinking, and walking through your code.  
  
And 𝘁𝗵𝗲 𝗽𝗮𝗿𝘁 𝗰𝗮𝗻𝗱𝗶𝗱𝗮𝘁𝗲𝘀 𝘀𝗸𝗶𝗽 𝗺𝗼𝘀𝘁 is the one that saves the most time: clarifying questions.  
  
*They hear the problem, recognise something similar from LeetCode, and start coding right away.* Then halfway through, they find out the array can have duplicates, or the input isn't sorted, or the output was supposed to be something else. Now they're rewriting code with half their time gone.  
  
"Can the input be empty?" "Are there duplicates?" "What should I return if there's no answer?" Each of these takes a few seconds to ask.  
  
Next time you practise on LeetCode, try this: before writing a single line, write down 3 questions you would ask the interviewer.
